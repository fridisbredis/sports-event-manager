## Purpose and scope

This document turns the product's non-functional expectations into measurable
requirements. It focuses on the four quality characteristics that matter most
before wider production use:

1. **Security** — protecting personal data, tenant isolation, access control,
   and the SMS integration.
2. **Performance efficiency and capacity** — keeping the application responsive
   as an event, its schedule, and its notification audience grow.
3. **Reliability** — transactional integrity, error handling, and
   observability, so failures are visible and recoverable rather than silent.
4. **Maintainability** — allowing a small team to change the product safely,
   understand its architecture, and release with confidence.

This is a quality plan, not a claim of ISO certification. Requirements marked
**Proposed** need product-owner approval before they become release gates.

### 2. Performance efficiency and capacity

**Note (2026-08-20):** the workload below replaces an earlier baseline (500
officials, 100 work areas, 50,000 assignments, 20 concurrent admin sessions,
1,000 concurrent read-only sessions, a 500-recipient audience) that had no
basis in real event data — it was invented by an earlier session and written
down as if it were agreed. This is an adjustment to correct that assumption,
not a bug fix; nothing in the system was wrong, the document was.

Two figures below are confirmed from the completed Viadal event. The
remaining three are **placeholders awaiting real figures from the product
owner** — rough estimates for sanity-checking only, not an agreed baseline.
PERF-01 through PERF-04 still depend on these numbers; this section is not
resolved until the placeholders are replaced.

**Acceptance method confirmed by the product owner (Peter Thorn, 2026-08-25):**
performance is judged relative to an unloaded baseline, not against a fixed
absolute threshold. For each test case (e.g. "switch view", "save schedule",
"send bulk SMS"):

1. Measure response time against an **unloaded instance** (no concurrent
   traffic) — this is that test case's baseline. Example given: "switch view"
   = 15 ms unloaded.
2. Measure the same test case under **simulated concurrent load** (for the
   level and role mix, see the derived figures below — Peter's example used 50,
   but that number was illustrative, not a requirement).
3. Express the loaded figure as a percentage of baseline. Example given: 95
   ms loaded = 633% of the 15 ms baseline.

**Ceiling confirmed by Peter (2026-08-25): 300% of unloaded baseline.** A
loaded figure at or below 3× the unloaded baseline for that test case passes;
above it fails. (The worked example above, 633%, is illustrative of the
calculation only — it would fail against this ceiling.) This replaces the
fixed "p95 ≤ 2s" criteria below — see PERF-01/PERF-02.

- One event with **20 officials** and **5 concurrent tenant-admin sessions**
  (confirmed: ~3 admins worked the event; padded to 5 for headroom, e.g.
  multiple sessions per admin).
- **Confirmed (Frida, 2026-08-27):** a typical tenant runs **3 event admins**
  (high load) and **10-15 officials** (low load per user), and the system
  should assume **5 parallel events**. The five events are separate tenants,
  not five events inside one tenant — every read filters on `tenant_id`, so
  co-locating them would overstate the per-query cost.
- **Confirmed (Frida, 2026-08-27): 200 assignments per event.** This replaces
  the earlier "~200-400" placeholder.
- **Placeholder — ~10-15 work areas per event.** Still estimated from typical
  race-event structure, not from Viadal data. `scripts/seed-perf.ts` defaults
  to 12 and prints the figure as PLACEHOLDER so a measurement report shows
  which inputs are agreed.
- **Placeholder — the announcement audience (participant count): unknown, no
  estimate given.** Depends on participant volume, which has no data point yet.
  Affects PERF-04, not the PERF-01 read paths.

**The "50 simulated concurrent users" figure is withdrawn (Frida,
2026-08-27).** It entered this document in commit `e0da050` alongside Peter's
confirmation of the _relative-baseline method_, where 50 appeared in his
worked example (15 ms → 95 ms = 633%). It was then written into PERF-01 and
PERF-02 as if it were an agreed load level, but nothing derives it from event
volume, and the confirmed figures above give ~18 sessions per event — 50 on a
single event does not occur in the described operation. The load level is
therefore derived from the confirmed volumes instead:

- **15 tenant-admin sessions** (5 events × 3 admins) on the heavy paths —
  dashboard and the stage-filtered scheduling view.
- **75 official sessions** (5 events × 15 officials) on the light paths — own
  schedule and event information.

The 300% ceiling itself is unaffected: it is a ratio against each test case's
own unloaded baseline, so it holds whatever the load level is.

**The local stack cannot serve the full 90 sessions, and this is a property of
the measurement rig, not a finding.** The local Postgres container runs
`max_connections = 100` with no pooler (`supabase_pooler` is not started by
`supabase start`), so at 90 concurrent sessions GoTrue begins failing with
`FATAL: sorry, too many clients already (SQLSTATE 53300)` — measured 2026-08-27:
230 GoTrue 500s, surfacing to the client as ~20% HTTP 307 redirects to `/login`
because the proxy could not validate a session. Any p95 taken at that level
measures connection exhaustion, not the read paths.

Runs at or below ~20 concurrent sessions stay clear of the ceiling (0% error
rate) and are the ones worth reading. A full-load figure needs either a pooler
in front of the local database or a prod-like environment; until then, treat
`--admins=5 --officials=15` as the honest local ceiling and say so alongside any
number quoted from it. See F-PERF-07 for what the sub-ceiling runs found.

Status 2026-09-01: **measured, not met.** The measurement environment is no

sessions cleanly, and the run completed with a 0% error rate. What it found is
a real capacity gap: the read paths fail the 300% ceiling from roughly 15
concurrent sessions upward at prod's current sizing. See **Result** below for
the numbers, the excluded suspects, and the two routes forward.

| Sessions | Verdict | Worst path |
| -------- | ------- | ---------- |
| 5        | PASS    | 212%       |
| 15       | FAIL    | 471%       |
| 30       | FAIL    | 1363%      |
| 90       | FAIL    | 2747%      |

**The knee is between 5 and 15 concurrent sessions per 3 replicas at 0.5 vCPU.**
The confirmed operational load is 90. That is the gap.

**What the bottleneck is — corrected 2026-09-01 after acting on the first
analysis.** The first pass concluded CPU was not saturated and the serial auth
prologue was the cause. **Half of that was wrong, and the error is instructive
enough to leave written down: the 43-58% figure came from
`az monitor metrics list --aggregation Average`, not `Maximum`, on the same
`CpuPercentage` metric.** Re-querying with `--aggregation Maximum` — verified
2026-09-02 against the perf environment — reads 20-30 points higher for a
comparable load, and a direct reading during a saturating run caught the
replica at **102% of its 0.5 vCPU limit**. CPU was saturated the whole time.
(An earlier draft of this correction attributed the gap to PT1M vs PT5M
interval granularity instead of aggregation type; that reasoning doesn't hold
— a five-minute maximum can never exceed the maximum of the one-minute buckets
it's built from — and has been withdrawn in favour of the verified cause
above.)

Each suspect, with what the measurement actually supports:

| Suspect                  | Measured                                  | Verdict                                         |
| ------------------------ | ----------------------------------------- | ----------------------------------------------- |
| Ingress / network        | 1102 rps when the app was idle            | Not the limit — but see below                   |
| PostgREST                | 1225 rps direct, p95 106 ms               | Not the limit                                   |
| Postgres                 | 1 active / 33 idle connections            | Not the limit                                   |
| GoTrue                   | p50 84 ms at conc 1 → 179 ms at conc 90   | Not the limit, but the largest single hop       |
| Per-request i18next init | 1.2-1.6 ms CPU                            | Negligible                                      |

The tell that settled it: `/api/health` — no auth, no database, same app
process — fell from **1102 rps to 120 rps** between an idle measurement and one
taken during load, with no code change to that route. A limit that moves an
untouched endpoint by 9× is not in the read paths.

**The serial prologue is real but was not the binding constraint.** It exists,
it was measured at 468 ms of dependent round trips (2 × 130 ms GoTrue plus
72 + 69 + 67 ms of PostgREST), and shortening it made every request measurably
cheaper. It just could not show up in the ratio while the CPU ceiling set
throughput: when every request is queueing, wait time is governed by service
rate, not by per-request cost. Both things were true at once, and the first
analysis credited the visible one.

#### What the optimisations achieved (PRs #107, #108)

Both were implemented and measured. Per-request cost — `min` latency under
load, i.e. the cost without queueing — fell as predicted:

| Path         | main   | +trim  | +trim+JWT |
| ------------ | ------ | ------ | --------- |
| dashboard    | 248 ms | 203 ms | 168 ms    |
| own-schedule | 251 ms | 196 ms | 142 ms    |

At 0.5 vCPU that bought nothing measurable, for the reason above. With the CPU
ceiling lifted it is worth a great deal:

| Configuration      | rps    | p95 dashboard | worst ratio |
| ------------------ | ------ | ------------- | ----------- |
| main, 0.5 vCPU     | 21     | 12308 ms      | 2747%       |
| both PRs, 0.5 vCPU | 17     | 10863 ms      | 2583%       |
| both PRs, 2 vCPU   | **89** | **2743 ms**   | 1198%       |
| both PRs, 4 vCPU   | 99     | 2078 ms       | 1014%       |

"worst ratio" is the highest ratio across all four read paths at that
configuration, not dashboard's own — dashboard is not necessarily the worst
path at every sizing. dashboard's own ratio at 2 vCPU is 2743 / its own
unloaded baseline at that sizing, not 2743 / 168 (the `min` under load from
the table above) — `min` and the unloaded baseline are two different
denominators, both reported because they answer different questions (per-
request cost without queueing vs. the PERF-01 ceiling itself). Neither table
records the per-path unloaded baseline at 2 vCPU directly; re-run
`perf:measure --baseline` at that sizing before quoting one.

**Absolute p95 improved 4.5× (12.3 s → 2.7 s). The ratio still fails**, partly
because the unloaded baseline improved too — a faster app has a tighter
baseline to be judged against, so the ceiling moves with it.

#### Where this leaves PERF-01

**More CPU will not close it.** 0.5 → 2 vCPU moved throughput 21 → 89 rps;
2 → 4 moved it 89 → 99 and the worst ratio only 1198% → 1014%. The return is
flattening well short of 300%. Doubling again is not a plan.

Three things are worth doing, and only the first two are ours to decide:

1. **Ship #105, #107 and #108 regardless.** They make the app measurably
   faster, are covered by tests, and cut p95 by 4.5× at a given sizing. That is
   real user-facing benefit whatever the ratio says.
2. **Raise prod to 2 vCPU / 4 GiB.** 0.5 → 2 is the one change that moved
   throughput by a factor. 2 → 4 is not worth the money on this evidence.
   Prod currently runs 0.5 vCPU (`deploy-prod.yml`), demonstrably
   under-provisioned for the confirmed operational load.
3. **Take the criterion back to the product owner.** 300% of an unloaded
   baseline is a demanding target when the baseline is ~250 ms: it requires
   p95 under 750 ms at 90 concurrent sessions on a server-rendered app. The
   question for Peter is whether the real requirement is "the app stays
   responsive under load" — where 2 s p95 may well pass — or literally 300%.
   **This is his call, not a measurement question**, and it should be asked
   before more engineering is spent chasing a number that may be stricter than
   the need. Note the ratio method's own property: it penalises a fast baseline,
   so optimising the app can make the ratio worse while every user's experience
   improves.

**Do not set `--max-replicas` from these runs.** Replica count was never the
constraint at this chain length; F-PERF-05's ceiling of 3 stays provisional.
Re-measuring is `npm run perf:measure` against the perf environment — the rig
is reusable and the seed reproducible. **Pin the replica count and CPU before
comparing two runs:** an early comparison in this session was invalid because
one run had 2 replicas and the other 3.

**What has already been fixed on the way here**

- [x] **F-PERF-07 — auth resolution was the dominant term.** Three
      `auth.getUser()` calls per admin render, each a GoTrue round trip.
      Resolved by memoising per render pass: GoTrue `/user` calls fell from ~5
      to 2.6 per page load and its p95 from 1748 ms to 217 ms, taking page p95
      from ~700-800 ms to ~535-551 ms. Auth is no longer the bottleneck.

Note that fixing F-PERF-07 did **not** move the verdict. It removed the largest
term and exposed the next one, which is the measurement rig itself. Read the
percentage columns with care: baselines fell too, so a ratio can worsen while
absolute latency improves — as it did here.

release record, and any relevant operational dashboard or alert has been
