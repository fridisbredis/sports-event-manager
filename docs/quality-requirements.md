## Purpose and scope

This document turns the product's non-functional expectations into measurable
requirements. It focuses on the four quality characteristics that matter most
before wider production use:

1. **Security** — protecting personal data, tenant isolation, access control,
   and the SMS integration.
2. **Performance efficiency and capacity** — keeping the application responsive
   as an event, its schedule, and its notification audience grow.
3. **Reliability** — transactional integrity, error handling, and
   observability, so failures are visible and recoverable rather than silent.
4. **Maintainability** — allowing a small team to change the product safely,
   understand its architecture, and release with confidence.

This is a quality plan, not a claim of ISO certification. Requirements marked
**Proposed** need product-owner approval before they become release gates.

### 3. Reliability

Reliability is a quality characteristic in ISO/IEC 25010 and previously had no
pillar in this document; findings about error handling, transactional
integrity, and observability had no natural home. PERF-05 and SEC-07 cover
parts of it — operability and audit events — both at `Should`. This pillar
makes it explicit and promotes observability to `Must`, because every finding
in this document is currently undiagnosable in production without it.

| ID     | Requirement                                                     | Acceptance criterion                                                                                                                                                                                                                         | Verification                                                                              | Priority |
| ------ | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | -------- |
| REL-01 | Multi-step operations must be atomic or explicitly compensated. | Every operation spanning more than one write executes as a single database transaction or RPC, or has a documented and tested compensating path. No write discards its error.                                                                | Integration tests with failure injection at each step.                                    | Must     |
| REL-02 | Failures must be observable.                                    | Structured logging, an error tracker, request and error metrics, and alerting on error-rate thresholds are in place. A health and readiness endpoint exists. No unhandled failure is silent.                                                 | Staging verification; deliberate failure injection producing an alert.                    | Must     |
| REL-03 | External-service calls must be resilient.                       | Twilio and Supabase calls have bounded retries with backoff, idempotency keys where the operation is repeatable, bounded concurrency, and recorded per-recipient or per-call outcome. Transient failures do not surface as request failures. | Staging test with a Twilio test double and injected transient failures. Overlaps PERF-04. | Must     |

## Definition of done for a quality requirement

A requirement is complete only when its implementation is merged, automated
verification passes in CI, the evidence is linked from the pull request or
release record, and any relevant operational dashboard or alert has been
verified in staging.
