# Quality Requirements — Addendum A

- **Attaches to:** [Quality Requirements and Initial Assessment](./quality-requirements.md) v0.1
- **Product:** Viadal Event Planner
- **Model:** ISO/IEC 25010 (SQuaRE) quality profile
- **Date:** 2026-08-11
- **Status:** Proposed additions, pending the same product-owner approval as v0.1
- **Verified against:** the working tree at commit `c78dbb4`

## Purpose and scope

This addendum adds findings and requirements that are not present in _Quality
Requirements and Initial Assessment_ v0.1. **It does not modify that document.**
It does not restate, replace, or renumber anything already in it. Identifiers
continue the existing scheme. Where an existing entry needs changing, this
addendum proposes the change in section 2 and leaves the original entry alone —
applying those proposals is the document owner's decision, not this addendum's.

**Evidence boundary.** Source-code review of the repository. Nothing was
verified against live Azure, Twilio, or production traffic. Every numeric claim
below was executed against the working tree on 2026-08-11.

## 1. A missing pillar

v0.1 covers Security, Performance efficiency and capacity, and Maintainability.
**Reliability** is a quality characteristic in ISO/IEC 25010 and has no pillar
there, so findings about error handling, transactional integrity, and
observability have no natural home. PERF-05 and SEC-07 cover parts of it —
operability and audit events — both at `Should`.

Section 4 therefore proposes REL-01 to REL-03, and the findings in section 3 use
`F-REL-` identifiers. If a fourth pillar is unwanted they fold into
Maintainability with the priorities unchanged, but observability should not stay
at `Should`: every finding in both registers is currently undiagnosable in
production, which is what F-REL-02 records.

**Priority scale used below,** matching v0.1's usage: `Critical` blocks further
external onboarding, `High` blocks the next production release, `Medium` blocks
the Viadal-scale event, `Low` gates nothing.

### Proposed changes to existing requirements

Proposals only. v0.1 is unchanged.

- **PERF-05** — split it. Operability under load stays; the observability half moves to REL-02 at `Must`. As written, a `Should` requirement is the only thing covering the condition that makes every other finding undiagnosable.
- **SEC-07** — extend to authentication. It covers invitation and SMS endpoints; the OTP login path is the one with no limiting at all (F-SEC-08). Its audit-event half is also currently unsatisfiable, because `sms_sent` is written `false` and never updated (F-SEC-04).
- **SEC-02** — require the role check at the data-access boundary, not only at the route boundary (F-SEC-02).
- **MNT-02** — widen the Prettier scope beyond `src/**`, so `docs/`, workflows, and root config files are gated (F-MNT-02).
- **MNT-03** — add MNT-08 as a stated prerequisite. Without it the integration suite is written against 9 to 18 module substitutions per file.
- **MNT-04** — the documentation conflict in F-SEC-03 is the first ADR this requirement should produce, since the C4 documents and the code currently disagree about service-role usage.
- **Capacity baseline** — internally inconsistent as proposed: 500 officials and a 500-recipient audience, but 1,000 concurrent read-only sessions. The read figure needs deriving from expected participant volume rather than asserting, because PERF-01 to PERF-04 all hang off it.
