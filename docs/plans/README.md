# Implementation plans

Plans for work packages that are large enough to think through before coding, or
that are blocked on a decision and need the reasoning to survive the wait.

A plan here is a **snapshot, not a contract**: it records what was verified, what
was assumed, and which questions were open at the time it was written. Once the
work lands, the code and the migration headers are the truth — the plan stays as
the record of _why_ it was built that way.

Each plan states at the top which commit it was written against, so a reader can
tell how stale it is.

Not every task needs one. Most work goes straight to a branch.
